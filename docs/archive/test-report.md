## Bugs (in order of severity)

1. **[Critical] In the keyboard test, the 3rd and 4th options cannot be selected, 3/3 correct cannot be achieved (`src/components/Test.tsx`):**
   - **What happened:** In the `<input type="radio">` options of the test questions, as soon as the `onChange` event fires the answer is recorded and all other options are made `disabled` (`disabled={cevap !== undefined && cevap !== index}`). When the keyboard user enters the question group with `Tab`, focus lands on the 1st option (`index = 0`); to move to the 3rd option in the radio group with the same `name` value (e.g. `"20"`, the correct answer in Ulu Camii question 1, `index = 2`), the moment they press `ArrowDown` / `ArrowRight` the browser selects the 2nd option (`"12"`, `index = 1`), fires `onChange` and locks the answer as wrong.
   - **How to reproduce:** On the `/eser/ulu-camii` page, using only the keyboard (`Tab`), go to question 1 in the `"Bilgini sına"` section and press the down arrow (`ArrowDown`) key to select the 3rd option (`"20"`), the correct answer.
   - **Expected:** It should be possible to move freely among all options using the arrow keys (or `Tab`) on the keyboard, and the answer should lock either with a separate `"Cevabı kontrol et"` button or when confirmed with `Enter`/`Space` (or the options should be presented as accessible buttons instead of radios).

2. **[Medium] When the numbered discovery point on the photograph is clicked, the information box that opens stays outside the visible area (`src/components/Galeri.tsx`):**
   - **What happened:** In the `onClick` handler of the `.bilgi-noktasi` button, right after `setAcikNokta(...)` is called, `document.getElementById('nokta-...')?.scrollIntoView({ block: 'nearest' })` is run synchronously (lines 60–61). Because the `<div>` inside a closed `<details>` is not yet visible in the DOM (`display: none`), the `scrollIntoView` called before React re-renders has no effect. Since the discovery points list sits below the photograph and the thumbnail strip (`y ≈ 1130–1230 px`), when the user clicks the number on the photograph they see no change on the screen.
   - **How to reproduce:** In a 1280×814 or 360×800 view, on the `/eser/ulu-camii` page switch to the 4th photograph (Şadırvan) and click the button numbered `3` on the photograph.
   - **Expected:** When the numbered button on the photograph is clicked, either an immediately visible information card should be shown next to/below the photograph, or after the `<details>` element has opened (via `useEffect` or via the `<details>` element itself) it should scroll to the relevant information box.

3. **[Medium] On first page load, because focus is moved to the `<main>` element, the "Ana içeriğe geç" link is skipped and the programmatic focus ring is hidden (`src/App.tsx`, `src/index.css`):**
   - **What happened:** `App.tsx` (lines 20–23) calls `document.getElementById('ana-icerik')?.focus()` on every `pathname` change (including the first open). Because `<main id="ana-icerik">` comes after the `.atlama` (`"Ana içeriğe geç"`) and `.ust-cubuk` (`"KökXR"`) elements in the DOM, when the user opens the page and presses `Tab` for the first time, focus jumps directly to the first artifact card; the `"Ana içeriğe geç"` link cannot be reached with the first `Tab`. Also, because of the `main:focus, h2:focus { outline: none; }` rule at line 44 of `src/index.css`, focus stops being visible during page transitions and in the test when the `"Sonraki soru"` button is pressed (`baslik.current?.focus()`).
   - **How to reproduce:** Open the home page (`/`) and press `Tab` once; focus goes directly to the Muradiye Külliyesi card instead of `"Ana içeriğe geç"`. In the test, answer a question and press the `"Sonraki soru"` button with `Enter`; focus moves to the `<h2>Bilgini sına</h2>` heading but the visible focus frame is lost.
   - **Expected:** On first load focus must not be forcibly moved to the `<main>` element (it should be moved only on in-page route changes), and the focus position must always be visually clear on elements focused with the keyboard.

4. **[Low] 404 Not Found error for `/favicon.ico` in the browser (`index.html`, `public/`):**
   - **What happened:** Because no `<link rel="icon" ...>` is defined in `index.html` and the file `public/favicon.ico` does not exist, the browser automatically requests `http://localhost:4173/favicon.ico` and gets a `404 Not Found` response.
   - **How to reproduce:** Open `http://localhost:4173/` in the browser and check the Network / Console tab.
   - **Expected:** An icon should be added under `public/` or a valid `<link rel="icon">` should be defined in `index.html` to remove the 404 error.

## Design suggestions (at most 5)

1. **Show the discovery point information right next to the photograph:** When the numbered buttons (`.bilgi-noktasi`) on the photograph are clicked, instead of the information opening in the `<details>` list far below the thumbnail strip, showing it directly right under the large photograph (in the figcaption area) or as an elegant information card over the photograph would strengthen the visual link between photograph and text.
2. **Remove the duplicate heading in the discovery points list:** In `Galeri.tsx`, when `<details className="nokta-detay">` is opened, the `<summary>` line says `"5. Güdük Minare"` while the `<h3>` tag right below it shows the heading `"Güdük Minare"` again (`04-kesif-listesi-guduk-minare-masaustu.png`). If the duplicate `<h3>` inside is removed, a cleaner look is obtained.
3. **Align the full-screen gallery buttons side by side in the phone view:** At 360 px width, the `"← Önceki fotoğraf"` and `"Sonraki fotoğraf →"` buttons in the full-screen (`<dialog className="tam-ekran">`) window break into two separate lines (`03-tam-ekran-telefon.png`). On mobile, having these two buttons share the same row with `flex: 1` saves vertical space and makes use easier.
4. **Visual emphasis on artifact cards when a badge is earned:** On the artifact cards on the home page, the `"★ Rozet kazanıldı"` label sits in the text flow under the heading (`07-anasayfa-rozet-masaustu.png`). Presenting the label with a prominent badge icon/colour in the corner of the card's cover image or aligned with the card heading would increase the feeling of success.
5. **Visually separate the wrong-answer box from the correct-answer box:** In the test section (`.yanit`), the same green left border (`border-left: 4px solid #235c4b`) and light green background (`#e9efe5`) are used for both correct and wrong answers (`06-test-yanlis-masaustu.png`). Using a border in a warm brick/amber tone (`#a24c15`) when a wrong answer is given would support the text notification visually as well.
